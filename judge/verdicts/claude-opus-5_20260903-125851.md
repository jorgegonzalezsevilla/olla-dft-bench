# Independent verdict — Olla-DFT benchmark run `20260903-125851`

- **Evaluator:** Claude Opus 5 (Anthropic), invoked from the benchmark author's Claude Code session with a clean context; same vendor as the model that wrote the benchmark harness (Claude Fable 5.1), so this is independent in context but not in provenance.
- **Date:** 2026-09-03 · **Run id:** 20260903-125851
- **Cross-check:** `bench.py verify results/20260903-125851` → `VERIFY PASS` (282 samples, hashes match, `report.md` byte-identical to regeneration). The report is an honest rendering of `results.json`; my disagreements are with design and framing, not arithmetic.

## 1. Fairness of design

Same inputs, fixed cutoffs, deterministic grading — defensible. Three constructions favour Olla-DFT:

- **kpath:** the reference is `seekpath.get_path` (HPKOT) and Olla-DFT calls seekpath internally (`qekit/core/kpoints.py:22`), so its ✔ on 5/5 structures is tautological, as seekpath's is; ASE and pymatgen get ✘ on 2 rows (Jaccard 0.60 / 0.09) for implementing Setyawan–Curtarolo. The note discloses this; the ✔/✘ column and coverage matrix do not.
- **eos:** `tools/reference.py` claims independence, but its BM3 fit reimplements `qekit/modules/eos.py` line for line — same form, same `np.polyfit` seed, same `p0=[E0,V0,B0,4.0]`, same `maxfev=20000`, same `160.21766208`. Hence Olla-DFT's ΔV0 = ΔB0 = **exactly 0.00e+00**, versus real disagreement for ASE (7.6e-08 Å³) and pymatgen (7.8e-07 GPa): circular, not accurate. Same pattern for symmetry (reference = ASE wrapper verbatim) and inputgen (ASE writes, ASE reads back).
- **bandgap:** defined as the data-file-schema XML, the one format only Olla-DFT reads. Both competitors parse pw.x *text* output, from which a gap is obtainable; choosing the XML turns a format preference into a coverage win.

**Missing competitors:** `qeschema` and `postqe` (QE's own Python packages, which read that XML) would contest the one task Olla-DFT wins uncontested; `aiida-quantumespresso` would contest inputgen.

## 2. Measurement validity

5 reps is thin and the dispersion shows it: IQR/median reaches **1.25** (symmetry/POSCAR_NaCl, olla), 0.83 (grafito, olla), 0.87 (kpath/POSCAR_NaCl, seekpath). All three environment warnings fired (`powersave`, turbo on, load 3.49), so individual medians are good to no better than ~±30 %. The conclusion survives anyway: on `min` (the noise-robust estimator) Olla-DFT is slower in **13/13** contested cells, **1.25×–1.71×** (median 1.31×); CPU-time ratios agree (1.12×–1.91×). Import cost is handled fairly (fresh process per rep for every tool, bias stated). Two flaws: tool order inside a repetition is **fixed** (Olla-DFT always first), not randomised; and the end-to-end stage is **n = 1** per tool, so "4.6 s vs 3.0 s" rests on one sample each.

## 3. Correctness of conclusions

The "areas of opportunity" list is **incomplete**: `benchlib/report.py:77` fires only above 1.5×, a threshold the report never states. Supported by the data but unlisted:

- Olla-DFT is slower in **all 13** contested cells, not 3: hbn 1.47×, POSCAR_NaCl 1.37×, all five kpath cells 1.23–1.43×, both inputgen cells 1.45×/1.49×, eos 1.11×.
- Peak RSS is higher in **13/13** cells (95–99 MB vs 77–81 MB; 1.20–1.29×). Never flagged, because 1.5× is never reached.

Conversely the two bandgap bullets ("2.9× slower", "98 MB vs 40 MB") are **spurious**: the "best competitor" is pymatgen's *unsupported* stub, which imported `pymatgen.core` and printed a refusal (0.23 s, 40 MB). `report.py` leaves unsupported cells in the `others` list. That bug over-accuses Olla-DFT rather than hiding anything.

Honestly reported and genuinely bad for Olla-DFT: 14 SCF iterations vs 7/8, pw.x 4.6 s vs 3.0 s at the same 13 k-points. Minor: the e2e text says "identical physics" while pymatgen used 24 irreducible k-points vs 13 — visible only in `results.json`.

## 4. Coverage honesty

Genuine. No `data-file-schema` string exists anywhere under the installed `ase/` or `pymatgen/`, and `pymatgen.io.pwscf` exposes only `PWInput`/`PWOutput`. Return codes are 0, `failed: 0`; no exception is relabelled. The only defect is that these cells still carry timings that leak into the opportunity rule (§3).

## 5. Reproducibility

Strong on the harness (hashes, lock file, `verify`, Dockerfile, QE workaround), broken on the subject under test:

- `requirements.lock:19` is `olla-dft @ file:///home/jorge/GITHUB/olla-dft` — a **local path**. `env.json` records `bench_git_sha` for the benchmark only; there is **no Olla-DFT commit**, contradicting PROTOCOL.md ("installed from its public repository at the commit recorded in env.json"). A third party cannot rebuild the tested version.
- No provenance for `Si.xml.gz` or `EOS.dat`: hashed, but the generating pw.x input is not shipped.
- Undocumented in the report: the 1.5× threshold, and that e2e is n = 1.

## 6. Verdict

- **Genuinely better:** the only tool here that reads pw.x `data-file-schema` XML, matching an independent ElementTree parse to 4e-06 eV; correct on every task it attempts (13/13 cells, 0 failures); its generated input reaches ASE's total energy to 3e-08 Ry.
- **Genuinely worse:** slower than the best competitor in **13/13** contested cells (1.25×–1.71× on best-case times, up to 1.90× on medians) and ~20 MB heavier in all of them; and its pw.x defaults cost **14 SCF iterations vs 7–8**, 4.6 s vs 3.0 s on identical physics — the most substantive finding of the run.
- **The benchmark should improve:** pin the Olla-DFT commit; stop grading against references that reimplement Olla-DFT's own algorithm or wrap its own backend; exclude unsupported cells from the opportunity rule.

**Overall confidence in the report: medium.** Numbers are exactly reproducible and nothing unfavourable is deleted, but the headline list understates a uniform ~1.3× speed and ~1.25× memory penalty while asserting two invalid ones, and two of three correctness wins are circular by construction.

## Improvements, most important first

1. Record the Olla-DFT git SHA in `env.json`; install from the public repo, not `file:///home/jorge/…`.
2. Exclude `unsupported` cells from `others` in `report.py:73–80` (removes the two bogus bandgap bullets).
3. Lower/parameterise the opportunity threshold (~1.15×), print it, and publish the full per-cell wall and RSS ratio table.
4. Make the eos reference truly independent (different parameterisation or analytic fit); flag any reference that coincides with a contestant's backend.
5. Raise reps to ≥15, randomise tool order per repetition, report a bootstrap CI on the ratio.
6. Add `qeschema`/`postqe` to bandgap and a second input in pw.x *text* format so ASE and pymatgen can compete.
7. Repeat the end-to-end stage (n ≥ 5) and show `nkpoints` in its table.
8. Ship the pw.x input behind `Si.xml.gz` and the recipe for `EOS.dat`; grade inputgen on the k-grid and cutoff it already prints, not only atoms and volume.
